# Threat model

What can go wrong when ShadowBench is run, and what can make its results
mean less than they appear to. Part A covers threats to the operator and the
machine running the benchmark; part B covers threats to the validity and
integrity of the results. Each entry names the mitigation that is actually
implemented, where it is documented, and the risk that remains.

## Scope and assets

| Asset | Why it matters |
|---|---|
| The operator's machine, accounts and credentials | Third-party tools and corpus content run or are read there |
| The committed corpora, labels, freezes and results | They are the evidence; every imported file is bound by SHA-256 in [`MIGRATION.json`](../MIGRATION.json) |
| The scoring rules | A rule change can move every number without a tool running again |
| Readers' conclusions | A misread result (an author-written run taken as field accuracy, an in-sample rerun taken as improvement) is the most likely harm |

Trust assumptions: the corpora are untrusted data; the tools under test are
untrusted code; the harness and scorer are trusted only to the extent they
are reviewed, and the repository history is the external record of when
anything changed.

## Part A: threats to the operator

| Threat | Implemented mitigations | Where documented | Residual risk |
|---|---|---|---|
| **Untrusted corpus content.** The corpora deliberately contain prompt-injection text, MCP launcher commands and simulated credentials. A human, an AI coding assistant or a tool that follows them could run commands or leak data. | The harnesses read, hash and copy corpus files and never execute them. [`tools/verify_migration.py`](../tools/verify_migration.py) checks bytes without importing or executing anything. Ruff and mypy exclude the estate artifacts. Synthetic credentials are approved only by exact path, credential family and SHA-256 in `tools/secret_allowlist.json`, and `tools/check_secrets.py` fails closed on anything else. [`AGENTS.md`](../AGENTS.md) tells coding agents never to execute corpus content. | Repository [README](../README.md); [`AGENTS.md`](../AGENTS.md) | An assistant or tool that obeys instructions found in the files is still exposed. Treat any automation that reads `benchmarks/` as handling hostile input. |
| **Corpus content executed by a tool under test.** Some tools enumerate MCP servers by launching them, or install dependencies. | Snyk Agent Scan runs with consent prompts declined (empty stdin), so no server starts. Estate wrappers for Cisco MCP Scanner and Snyk Agent Scan put refusing shims for common launchers (`npx`, `npm`, `node`, `uvx`, `pipx`, `python3`, `docker` and others) first on `PATH`. cdxgen runs with `--technique manifest-analysis --no-install-deps`. | Estate [Execution and isolation](../benchmarks/shadowbench/estate/README.md#execution-and-isolation); discovery [Isolation and fairness](../benchmarks/shadow-ai-discovery/README.md#isolation-and-fairness) | Only the shimmed names are refused: `sh`, `bash`, `perl`, `curl`, an absolute command path or a configuration that sets its own `PATH` still runs. The committed 2026-10-11 estate run predates the shims. |
| **Malicious or compromised repositories fetched for the code surface.** | The cases track's `fetch_code` runs only `git`, with `https` remotes only, hooks disabled, no submodules, no filter drivers (a repository's `.gitattributes` cannot start git-lfs), none of the operator's system or global git configuration, the caller's `GIT_*` variables dropped, TLS verification on, no symlinked destination, and the fetched commit checked against the pin before and after checkout. The cases runner refuses a checkout with anything beyond its pinned tree. The code-surface `fetch` delegates to the same `fetch_pinned` and `checkout_problem`, so it applies the same rules and `--verify` reports a checkout that holds anything beyond its pinned tree. | [`fetch_code.py`](../tools/shadowbench/cases/fetch_code.py) docstring; cases harness [Reproduce](../tools/shadowbench/cases/README.md#reproduce); [`fetch.py`](../tools/discovery_benchmark/fetch.py) | A pinned commit can itself contain hostile content; the tools then read it. Before the 2026-10 amendment ([`AMENDMENTS.json`](../AMENDMENTS.json)) the code-surface `fetch` passed the caller's environment and git configuration to `git` and kept any checkout whose `HEAD` matched; checkouts made by that version should be fetched again. |
| **Third-party tools run with the operator's privileges.** | **Cases:** each tool runs as uid/gid 65534 with no supplementary groups and `no_new_privs`, in fresh network, PID, mount, IPC, UTS and cgroup namespaces, with the host name `shadowbench` (and read-only `/etc/hostname` and `/etc/hosts` naming it), resource limits `prlimit` sets in each tool's own process (no core dumps, bounded file size, open files and processes), `/root` and `/home` under empty tmpfs mounts, fresh `/var/tmp` and `/dev/shm`, and an environment built from scratch. `--sandbox oci` runs the same inside a digest-pinned container with a read-only root, only the run directory writable, all capabilities but four dropped for the stage and none for tools, Docker's seccomp profile and memory, CPU and pids limits; `--oci-runtime runsc` adds gVisor. **Estate and discovery:** a rebuilt environment (no API keys, private `HOME` and `TMPDIR`, telemetry opt-outs) and, with `--as-user`, a `setpriv` drop to another account. | Cases harness [Isolation](../tools/shadowbench/cases/README.md#isolation); [harness.md](harness.md); [supply-chain.md](supply-chain.md#sandbox-backends) | Under the default backend a cases tool can read anything world-readable outside `/root` and `/home`, and shares the host kernel. Under `oci` with `runc` it still shares the host kernel; gVisor support is a runtime flag not exercised by this repository's tests. Estate and discovery tools run with no namespaces, as the invoking account unless `--as-user` is given; the 2026-10-11 estate run did not use it. |
| **Supply chain of the tools under test.** | Cases-track PyPI tools install exactly the distributions of committed hash locks (`--require-hashes --no-deps`, then `uv pip check`); Go tools build from pinned commits against `go.sum` in `-mod=readonly` mode, the Fleet wrapper against a committed `go.mod` and `go.sum`; Go modules are checked against the Go checksum database. Each venv is created afresh, and an sdist-only distribution is built against hash-locked setuptools without build isolation. The installed set is recorded (`resolved/`: freeze lists, Go build info with module hashes, SHA256SUMS) and copied into every run, and the runner re-hashes every recorded binary and entry point and refuses to start if one changed. The tool image builds from digest-pinned base images. | [supply-chain.md](supply-chain.md#hash-locked-tool-installs); [`install_tools.sh`](../tools/shadowbench/cases/install_tools.sh) header | A lock pins what PyPI served when it was compiled; a malicious release already in the lock is installed faithfully. Venv library files are covered by the locks and freeze lists, not re-hashed at run time. The image's build-stage Debian packages are not pinned (they are not in the exported tree). Estate and code-surface tool installs are not hash-locked. The 2026-10-11 runs predate the locks. The installer downloads and runs third-party code. |
| **Symlink, hard-link and TOCTOU attacks on the work tree.** A tool's uid could plant a link that makes root read or write another file when the adapter reads the output. | Cases: the scratch directory must be mode 0711 and owned by the runner; `control/` is root-only; after the stage exits the runner takes `work/` back for root and removes group and other write before removing escaping symlinks; hard links, FIFOs, sockets and device nodes are removed rather than handed to root; inputs are written without following symlinks at any path step. Estate with `--as-user`: capture files and `result.json` are created through a directory descriptor, never by path; both trees are taken back and every symlink, hard link and special file is removed without being followed. | [`runner.py`](../tools/shadowbench/cases/runner.py) docstring; estate [Execution and isolation](../benchmarks/shadowbench/estate/README.md#execution-and-isolation) | Without `--as-user`, an estate tool runs as the operator and needs no link tricks. |
| **Version probes.** A probe runs the tool's binary outside the per-case isolation. | Cases probes get a fixed `PATH`, a throwaway `HOME`, an empty stdin and a timeout; as root they get an empty network namespace, a fresh PID namespace and hidden homes, and drop to uid/gid 65534 with `no_new_privs`, or do not run. A `version` in `tools.json` skips the probe. | [`adapters/_probe.py`](../tools/shadowbench/cases/adapters/_probe.py) docstring | Estate and discovery probes run before the matrix as the invoking account with its own environment. |
| **Leftover processes.** A tool can detach a child that survives the case. | Cases: after each invocation the stage stops every process in the namespace, kills and reaps all but the inert processes, and fails the case if any survives; on overrun the runner kills the namespace. Estate and discovery kill each command's process group on timeout. | [`stage.py`](../tools/shadowbench/cases/stage.py) docstring | A detached process outside the process group can survive in estate and discovery runs. |
| **Host `/tmp` persistence across cases and tools.** | Cases give each case fresh `/var/tmp` and `/dev/shm`; under `--sandbox oci` each case also gets a fresh `/tmp` and sees only its own run directory. | [`stage.py`](../tools/shadowbench/cases/stage.py) docstring | Under the default backend the host's `/tmp` (which usually holds the scratch directory) is shared with the host and with later cases and tools, so one tool's files can be read by another or change a later result. |
| **Network egress and data leaving the machine.** | Cases: an empty network namespace, with `/run` and `/tmp/.X11-unix` covered so no host service's UNIX socket (the D-Bus system bus, whose systemd-resolved interface resolves names, nscd, an X server) bridges it; mock services are bound to `127.0.0.1` whatever the case says and refuse malformed or oversized requests. Estate and discovery: a dead proxy (`http://127.0.0.1:9`) unless `--keep-network`. | [`mockserv.py`](../tools/shadowbench/cases/mockserv.py) docstring; discovery [Isolation and fairness](../benchmarks/shadow-ai-discovery/README.md#isolation-and-fairness) | The dead proxy only stops clients that honour proxy variables. Some tools send telemetry or scan metadata to their vendor (the discovery README records Snyk Agent Scan doing so in verbose mode). Under `--sandbox namespaces` a socket another host process leaves elsewhere in the shared `/tmp` stays reachable; `--sandbox oci` sees none. Disable egress outside the harness. |
| **Credential exposure.** | Tool environments are built from scratch (`contract.base_env`, the estate and discovery scrubbed environment); cases hide `/root` and `/home`, and the runner and stage join a new, empty session keyring before anything starts, since a uid change keeps the session keyring and its keys stay readable to whoever possesses it. | [`contract.py`](../tools/shadowbench/cases/contract.py) | Estate and discovery tools can read the invoking account's files. Use a machine with no credentials. |
| **Machine paths and identities in published records.** Run records name the operator's directories, user and host. | The cases runner writes rows with its tool root, scratch, output and harness paths already replaced, before their digest is taken. `python -m tools.shadowbench.scrub apply` replaces mapped paths (and with `--host` the host name) in the other records where a path starts and ends; `scrub check --identity` reports home, temporary and profile paths and the host and user names left; `make paths` and CI check every committed results directory of the live tracks, skipping only paths the corpora themselves contain. Tools in the cases stage see the host name `shadowbench`. | [supply-chain.md](supply-chain.md#scrubbing-machine-paths); [submitting-results.md](submitting-results.md#what-never-to-commit) | The check matches patterns; a private path in another shape, or a name inside free text, can pass. Two legacy results files bound by `MIGRATION.json` (`tools/benchmark/realworld/results/environment.json`, `tools/benchmark_realworld/results/REPORT.md`) name `/home/user` and are not checked. |
| **Unsafe identifiers in the corpus.** A case or unit id could name a path outside the work tree. | Case, checkout and unit ids must match `[A-Za-z0-9._-]+`; the estate walk refuses symlinks and special files; migration paths must be canonical and relative. | [`runner.py`](../tools/shadowbench/cases/runner.py); [`verify_migration.py`](../tools/verify_migration.py) | None known. |

## Part B: threats to validity and integrity

| Threat | Implemented mitigations | Where documented | Residual risk |
|---|---|---|---|
| **Conflict of interest.** One maintainer wrote ShadowScan, both ShadowBench tracks, the code-surface benchmark, every corpus, every label and every other tool's adapter, with AI assistance. | Disclosed at the top of every track README; every input, adapter, row and rule is committed so someone without a stake can rerun it. No letter grades are published. | [ShadowBench README](../benchmarks/shadowbench/README.md); estate [Bias and limits](../benchmarks/shadowbench/estate/README.md#bias-and-limits) | Unresolved until an independent party reruns the benchmark, ideally with their own corpus and labels ([submitting-results.md](submitting-results.md)). Any ShadowScan lead is suspect. |
| **Trigger knowledge and format selection.** The author knew ShadowScan's documented detection triggers, and the estate's artifact formats are ShadowScan's offline export formats. | Hard positives beyond documented triggers; negatives ShadowScan itself over-flags; per-entity rationale; per-surface tables and exclusion notes alongside the headline. | Estate [Bias and limits](../benchmarks/shadowbench/estate/README.md#bias-and-limits) | Tools whose native mode is a live API or the kernel cannot show their strength on an offline corpus. |
| **In-sample tuning.** ShadowScan's rules changed after the 2026-10-11 estate run with its twelve errors in view; the 2026-10-09 code-surface run followed benchmark-driven changes on the same corpus. | The 2026-10-11 estate run stays the run of record; the in-sample replay is not published; the 2026-10-09 results are labeled as measuring fit to the corpus. | Estate [Bias and limits](../benchmarks/shadowbench/estate/README.md#bias-and-limits); discovery [Results (2026-10-09)](../benchmarks/shadow-ai-discovery/README.md#results-shadowscan-after-the-benchmark-driven-changes-2026-10-09) | Measuring those changes needs a corpus authored without sight of the errors. |
| **Answer-key leakage into predictions.** The AI-Infra-Guard estate adapter of the time appended each mock service's `services.json` anchor (the answer key) to the prediction text, disclosure [a]. | The current adapter records scan targets instead, and the scorer counts such predictions as `harness_attributed`, not as the tool naming the host. | Estate [Disclosures for the 2026-10-11 run](../benchmarks/shadowbench/estate/README.md#disclosures-for-the-2026-10-11-run) | The committed `runs.json` keeps the appended text, so the committed score still attributes both predictions through it; without it they are false positives (0/6). |
| **Answer key within a tool's reach (cases).** A tool under test is untrusted code, and a discovery tool scans the file system: the labels it is scored against, and the benchmark's own fixtures, should be out of its sight. | The stage runs from a root-only copy of the six modules it imports (`STAGE_MODULES`), so neither backend shows a tool the harness's corpus, generator or families. Under `--sandbox namespaces` it also covers the harness checkout and `--out` with an empty tmpfs, `--corpus` with an empty read-only file, and every entry of a configured ShadowScan checkout but its `shadowscan/` package and the paths `tools.json` names; `--sandbox oci` binds only that package of it. Version probes hide the same paths, and the runner refuses a scratch or tool path under any of them, by its configured spelling or what it resolves to. Run directories are named `run-XXXX`, and `case.json` no longer carries the case id. | [`runner.py`](../tools/shadowbench/cases/runner.py), [`stage.py`](../tools/shadowbench/cases/stage.py) and [`_probe.py`](../tools/shadowbench/cases/adapters/_probe.py) docstrings; [harness.md](harness.md#isolation) | The corpus is public, so a tool could ship answers keyed by its inputs' content; no sandbox stops that, and only new, unpublished cases would. Results of other runs kept outside the checkout and `--out`, and any other world-readable copy of the corpus, stay readable under `--sandbox namespaces`. Before this change a checkout outside `/root` and `/home`, a ShadowScan checkout, the results and a corpus kept elsewhere were readable under `--sandbox namespaces`, and `--sandbox oci` bound the whole `tools/` package and the whole ShadowScan checkout; runs made then are affected. |
| **Wrappers that hide failure.** The Cisco MCP Scanner and AgentSight wrappers always exited 0 and their normalizers read missing reports as empty, disclosure [b]; Agentic Radar's adapter accepts exit 1, disclosure [c]. | Current wrappers exit with the first failing step's status; normalizers treat missing, empty or unparsable reports as errors; the estate completeness rule makes a unit whose every command exited non-zero with no output incomplete. Adapters across tracks must fail closed. | Estate [Disclosures](../benchmarks/shadowbench/estate/README.md#disclosures-for-the-2026-10-11-run) and [Run completeness](../benchmarks/shadowbench/estate/README.md#run-completeness); [adding-a-tool.md](adding-a-tool.md) | The committed run's `ok` statuses and true negatives for those tools do not show clean runs. No stderr was committed, disclosure [d], so accepted non-zero exits cannot be audited from the published results. |
| **Generator seed with no effect, shared random streams.** The committed cases corpus was built with a derivation under which every seed builds the same cases and four pairs of modalities share one stream; the adapters' smoke corpus drew from the scored corpus's streams. | New corpora seed each stream from a SHA-256 of seed, surface and modality and record `"stream_scheme": "sha256"`; `verify` prints the scheme and any shared streams; `legacy` is kept only to rebuild the committed cases. | Cases [Random streams](../benchmarks/shadowbench/cases/README.md#random-streams) and [Bias controls](../benchmarks/shadowbench/cases/README.md#bias-controls) | The committed results show nothing about variation across seeds, and the calibration corpus was not an independent draw. |
| **Edited, swapped or truncated results.** | Cases: the manifest records the corpus SHA-256 and each `<tool>.jsonl`'s `rows_sha256`; the scorer refuses a mismatch unless `--force` and records every override; malformed rows are refused even with `--force`. Estate: the freeze manifest digest and post-run drift are recorded and checked. All imported files are bound in `MIGRATION.json`; harness changes since are chained in `AMENDMENTS.json`, which cannot amend evidence. The three historical result directories have digest manifests signed keylessly with Sigstore by the `attest.yml` workflow on `main` and logged in Rekor; `make verify` and CI require all three signatures and fail on missing bundles, changed result files or failed verification. The weekly clean-room workflow re-scores the cases and estate 2026-10-11 runs (metrics and reports) and the code-surface 2026-10-09 metrics from scratch; older historical results are not re-scored. | Cases [Metrics](../benchmarks/shadowbench/cases/README.md#metrics); [harness.md](harness.md); [supply-chain.md](supply-chain.md#signed-results) | The 2026-10-11 cases run manifest predates `rows_sha256`, so every tool there is `rows_unbound`: an edited file that keeps the status counts could pass that scorer check alone. The [verified signatures](historical-attestations.md) separately bind those bytes, but attest what the maintainer's automation saw, not that it was honest or independently executed. The scorer's own commit is not recorded, and the code-surface `runs.json` records no corpus digest or harness commit. |
| **Scoring rules revised after seeing results.** | Revised rules were re-applied to the unchanged rows, and every change and its effect on the numbers is listed. | Cases [Bias controls](../benchmarks/shadowbench/cases/README.md#bias-controls) and [Integration changes](../benchmarks/shadowbench/cases/README.md#integration-changes); estate [Results](../benchmarks/shadowbench/estate/README.md#results) | The published metrics come from rules written with the run's results in view; the adapters were also changed after the run. |
| **Label errors and labeler bias.** | Code-surface labels come from objective evidence rules and were audited against every tool's false positives in both directions (corpus v2); the estate had a label-completeness audit, and errata are recorded rather than silently applied. | Discovery [How ground truth was labeled](../benchmarks/shadow-ai-discovery/README.md#how-ground-truth-was-labeled); estate [Corpus](../benchmarks/shadowbench/estate/README.md#corpus) | One labeler, who maintains one of the tools. No independent human labeling. |
| **Anchor collisions and reach.** Estate attribution matches entity anchors in prediction text; 12 anchors also occur outside their entity's artifacts, and reach is decided by the unit, not by what a tool read. | `validate` warns on every collision (`--strict` fails); attribution considers only entities on the prediction's surface; ambiguous attributions are counted and listed. | Estate [Attribution](../benchmarks/shadowbench/estate/README.md#attribution) and [Bias and limits](../benchmarks/shadowbench/estate/README.md#bias-and-limits) | A prediction on the colliding entity's surface can still be attributed through a collision; fixing it needs a new freeze. |
| **Synthetic inputs and approximate mocks.** Eight cases-track surfaces are synthetic; active-network mocks reproduce banners and endpoints, not applications. | Inputs use the platforms' own shapes; decoys come from confusions real tools make. | Cases [Known limits](../benchmarks/shadowbench/cases/README.md#known-limits) | Real tenants are larger and messier. The decoy mocks' answer to unknown paths was settled with AI-Infra-Guard's response in view. |
| **Small samples.** Twenty cases per modality on most cases-track surfaces; one 137-entity estate. | Wilson intervals for precision, recall and specificity; case-bootstrap F1 intervals; exact McNemar tests; `--per-surface` can be raised. | Cases [Metrics](../benchmarks/shadowbench/cases/README.md#metrics) and [Known limits](../benchmarks/shadowbench/cases/README.md#known-limits) | Intervals are wide; the estate cannot measure field base rates or scale behaviour. |
| **Weaker isolation in committed runs.** The 2026-10-11 cases rows were recorded with tools and inert processes running as root and the host's homes in view (Fleet's table saw them). | The current runner's isolation; the report states that the rows come from earlier adapters under weaker isolation. | Cases [Integration changes](../benchmarks/shadowbench/cases/README.md#integration-changes) | Committed rows cannot be re-derived under the current isolation without a new run. |
| **Unverified tool versions.** | The runner records the version a tool's `tools.json` entry gives or what its adapter probes. | Cases [Tools](../benchmarks/shadowbench/cases/README.md#tools) | A configured `version` is recorded as given, unchecked. The estate run recorded ShadowScan only as `0.1.2`, not a commit. |
| **Misattributed provenance from legacy helpers.** Historical freeze and self-check helpers hash `<repository root>/shadowscan` and record the repository's commit. | The repository README and [harness.md](harness.md) say to run them only in a ShadowScan checkout at the source commit. | Repository [README](../README.md) | Run from this companion they would hash an empty scanner tree and record the companion's commit as a scanner revision. |
| **Baseline selection by directory order.** ShadowScan's weekly regression workflow treated the last-sorting directory under `benchmarks/shadow-ai-discovery/results/` as its baseline. | Since [aisecnomad/Nexus-ShadowScan#289](https://github.com/aisecnomad/Nexus-ShadowScan/pull/289) the workflow names its baseline in `BASELINE_RUN`, fails when that directory lacks `metrics.json` or `runs.json`, and reports a later directory without using it. | [ShadowScan `benchmark.yml`](https://github.com/aisecnomad/Nexus-ShadowScan/blob/main/.github/workflows/benchmark.yml); [submitting-results.md](submitting-results.md) | Moving the baseline is a one-line change in ShadowScan; it needs review like any change to the gate. |
| **Citing unverifiable numbers.** The ShadowBench-450 archive holds author-supplied counts without fixtures, labels, adapter sources or per-case predictions. | Marked unverified; rankings, grades and recommendations withdrawn; `python -m tools.shadowbench450_archive` checks arithmetic and consistency only. | [ShadowBench-450 archive](../benchmarks/shadowbench-450/README.md) | Its counts can still be quoted out of context. They are not evidence of product performance and are not comparable with either track. |

## Operating rules that follow

1. Run third-party tools only on a disposable, externally isolated machine
   with no credentials and egress disabled. Scoring and reporting committed
   results need no third-party tool.
2. Use the cases runner's isolation as the floor; for estate and discovery
   runs always pass `--as-user` with a dedicated account.
3. Read corpus files as data. Do not let an assistant act on what they say.
4. Never overwrite a committed result, freeze or corpus; write new runs to
   new directories and disclose everything
   ([submitting-results.md](submitting-results.md)).
5. Read every result with its track's "Read this first" note and its
   disclosures. Author-written runs are evidence about the listed inputs,
   not field precision or recall and not a verdict on any product.

## Reporting

Report a vulnerability in the harness (an isolation escape, a path or link
attack, a way to make the scorer accept rows its manifest does not vouch
for) or a real credential found in the corpus privately, as described in
[SECURITY.md](../SECURITY.md), through a GitHub private advisory:
<https://github.com/aisecnomad/Nexus-ShadowBench/security/advisories/new>.
Do not open a public issue for these. Validity problems (a label error, an
undisclosed in-sample run, a scoring rule that misleads) are welcome as
public issues.
